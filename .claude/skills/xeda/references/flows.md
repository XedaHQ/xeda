# Flow catalog

Generated by `xeda skill install` from the installed version of xeda. Regenerate after upgrading xeda, or when a flow is added.

Settings are deliberately not listed here (there are several hundred). For any flow:

```bash
xeda list-settings <flow> --json     # every setting: name, type, default, meaning
xeda list-results <flow> --json      # every metric: path, type, unit, meaning
```

Flows with declared file I/O chain with `+`: `xeda run yosys_fpga+nextpnr+fpga_pack design.yaml` binds each flow's declared outputs to the next flow's required inputs. "can follow" and "can be followed by" below are the declared relations; `(depends on the target)` marks one the target's family decides, and `flow.output+flow` one that needs the output named. `(through a, b)` marks a relation whose link passes through the flows `a` and `b` between the two: Xeda runs them as it does for the second flow alone. A refused chain says which chain would be valid, if any. The relations are declarations only: planning can still refuse a chain that passes (related inputs). For example, `yosys_fpga+vivado_impl+vivado_power` also needs `-s flows.vivado_postsynth_sim.inputs.<input>=vivado_impl.<input>` for each of `netlist`, `netlist_timing` and `sdf`; the refusal lists the bindings to add. A flow with no declared I/O runs alone.

## Simulation

### `bsc_sim`

Simulate a Bluespec testbench compiled by bsc, with Bluesim or a Verilog simulator. The flow compiles the design's Bluespec sources in order, RTL first and then the testbench, with the package that defines `tb.top` last. It simulates `tb.top`, a module with an `Empty` interface (`rtl.top` when the design has no testbench). `simulator` selects Bluesim, the cycle-based simulator of bsc, or a Verilog simulator that bsc links with the generated Verilog (`bsc -vsim`). The clock and reset come from the `main.v` of bsc. Bluesim records the system-task calls in the generated code, and a script of Xeda measures the clock cycles and the time. Verilator and Icarus record the system tasks that the linked runtime observes. For these three simulators, a run passes only if the testbench finishes explicitly (or Bluesim reaches a confirmed `max_cycles` limit) and no event reaches `fail_severity`. A fatal error or a nonzero exit status always fails the run. `$finish(n)` uses `n` as a verbosity level. The design's `defines` and `parameters` are preprocessor macros, and the testbench's go over the RTL's. BH (`.bs`) sources see them only through the C preprocessor, with `cpp`. The supported simulators are Bluesim, Verilator, Icarus, ModelSim, Questa, VCS, vcsi and xsim. The legacy simulators cvc, cver, isim, ncverilog and veriwell are rejected before compilation. The Linux CI job checks the real Icarus evidence and the registration of the built-in tasks.

76 flow-specific settings (plus the common ones): `xeda list-settings bsc_sim --json`

Reports: `sim.evidence`, `sim.ended_by`, `sim.time`, `sim.time_unit`, `sim.errors`, `sim.warnings`, `simulator`

### `modelsim`

*can follow: `bsc`*

### `verilator`

*supports cocotb testbenches | can follow: `bsc`*

Simulate a Verilog or SystemVerilog design with Verilator 5.048 or newer. Verilator compiles the design to C++ or SystemC and builds a native executable. The flow supports cocotb testbenches, plain C++ and SystemC harnesses, and VCD, FST and SAIF waveform tracing. Three drivers run the model. By default, Verilator's own `--main` runs an HDL top (the `main` setting). With `main: false`, the design's own C++ `main` or `sc_main` runs it. With cocotb, cocotb's own main runs it, and cocotb's results decide the run. The simulated top module is `tb.top`, else `rtl.top`. A design with HDL testbench sources needs `tb.top` when Verilator supplies its main. With cocotb, the simulated top module is the one cocotb drives: `tb.cocotb.toplevel`, else `rtl.top`. The parameters (`-G`) are `rtl.parameters` updated by `tb.parameters` when the simulated top module is the RTL top, and `tb.parameters` alone otherwise. Without cocotb, a run passes only on evidence of how the simulation ended. Xeda's hooks record that evidence in Verilator's runtime (`xeda_end.json` in `sim_dir`). Under Verilator's main, the run passes when the testbench ends it with `$finish` and nothing reported reaches `fail_severity`. An event queue that runs empty without a `$finish` fails. Under the design's own main, the run passes when that main exits with status 0 and nothing reported reaches `fail_severity`. The flow refuses `stop_time`: end the testbench with `$finish`, or use `timeout`. A waveform setting (`vcd`, `fst` or `saif`) builds the model with that trace format. Without cocotb, the testbench's `$dumpfile` and `$dumpvars` (or the design's own main) write and name the file. Xeda opens no waveform.

### `nextpnr`

*runs first: `yosys_fpga` | can follow: `yosys_fpga`, `bsc` (through `yosys_fpga`) | can be followed by: `fpga_pack` (depends on the target), `openfpgaloader` (through `fpga_pack`) (depends on the target)*

Place and route an FPGA design with nextpnr. The input `netlist` is a `JsonNetlist` design source or, by default, the netlist that `yosys_fpga` produces. ### `openfpgaloader`

*runs first: `fpga_pack` | can follow: `fpga_pack`, `vivado_alt_synth`, `vivado_impl`, `vivado_synth`, `bsc` (through `yosys_fpga`, `nextpnr`, `fpga_pack`), `nextpnr` (through `fpga_pack`) (depends on the target), `yosys_fpga` (through `nextpnr`, `fpga_pack`) | programs a device and can only end a chain*

Program a bitstream onto an FPGA board with openFPGALoader. The `bitstream` input is a typed `Bitstream` design source (a file built elsewhere, by any toolchain) or, by default, the `bitstream` output of `fpga_pack`. The flow builds and packs nothing itself. The settings of the earlier stages belong to their own sections (`flows.nextpnr`, `flows.fpga_pack`). The flow selects the device with `cable`, else with the name of the board in openFPGALoader (`openfpgaloader_board` in the board database) when the board has one. The flow passes the FPGA part when the part is known and either `cable` is set or no board name is passed: a Xilinx part without its speed grade, any other part as it is. Without a part, openFPGALoader detects the device. Programming the flash (`write_flash`) needs the part. The loader opens the first probe that fits the cable's USB id, before it reads any ID code, so with two boards of one kind connected it can program the wrong one. The flow chooses the probe when the run names none (no `usb_serial_num`, no `cable_index`, and none of `--ftdi-serial`, `--usb-serial-num`, `--cable-index`, `--busdev-num`, `--vid`, `--pid`, `--device` or `-d` in `extra_args`), `extra_args` gives no other cable or board, and the cable and the part are known. The cable is the `cable` setting, else the cable that openFPGALoader lists for the board. The flow asks the loader for the probes that fit the cable (`--scan-usb`). With two or more, it reads the FPGA of each (`--detect`, with `--board` when the cable comes from the board, else with `--cable`) and programs the probe whose FPGA matches the part, named by its serial number (`--ftdi-serial`). `--detect` reads the JTAG ID code and does not configure or reset the FPGA, but it opens every probe with that USB id, a debugger included. `usb_serial_num` skips it. The flow programs a probe only when exactly one probe matches and every other probe was read and shows another device. Otherwise it fails before it programs anything: no probe matches, several match, or one matches beside a probe that could not be read (that probe may be a second board with the same FPGA). The message lists each probe with its device, or why it could not be read, and the `usb_serial_num` setting that names it. Xeda does not choose a probe and warns when several probes fit the cable and Xeda cannot name one reliably: no part is known; Xeda cannot match the part to the loader's model names (iCE40, Spartan-6, MachXO3, Arria 10 and others); the cable is a bit-bang cable given with `cable` (`ft231X` or `ft232RL`); the probes are not FTDI chips; or a probe has no serial number, shares its serial with another, or the scan cannot read its serial. It also warns when the loader cannot list its boards, cables or probes, or when the scan cannot be read or could not open a probe. In these cases openFPGALoader then chooses the first probe that fits the cable. Xeda names a probe only by the serial number of an FTDI chip, because `--busdev-num` works only with libftdi 1.4 or newer, which Xeda cannot detect. The queries run in `run()` only, outside the run directory, with a time limit, and never write `openfpgaloader.log`. The flow logs its choice. The flow keeps the output of the loader in `openfpgaloader.log` in the run directory. It needs openFPGALoader 0.13.1 or newer and refuses an older loader before it builds or programs anything. The run fails when the loader exits with a nonzero status. It also fails when the output shows that the device was not programmed although the status is 0: DONE low after a Xilinx load (with the ID or CRC error that the FPGA reports), a step that printed FAIL, or an error message such as a flash that does not answer. A flash write on a Xilinx FPGA also fails unless the loader reports that it wrote the flash. The flow always runs, because it changes a device and no file. It is the only built-in flow that programs a device.

### `vivado_impl`

*runs first: `yosys_fpga` | can follow: `yosys_fpga`, `bsc` (through `yosys_fpga`) | can be followed by: `openfpgaloader`, `vivado_power`*

Place and route a netlist with AMD-Xilinx Vivado, in non-project mode. The `netlist` input is an `Edif` design source or, by default, the EDIF netlist that `yosys_fpga` writes for a flat Xilinx synthesis. So `xeda run yosys_fpga+vivado_impl design.yaml` implements the open-source synthesis with Vivado. Vivado does no synthesis here. A generated TCL script reads the constraints and the netlist, links the design, and runs `opt_design`, `place_design` and `route_design` on it in memory, with the optimizations that `impl` asks for (the default strategy adds `opt_design` and `phys_opt_design` after placement). The flow reports timing and utilization. It writes a bitstream when `bitstream` is set or a consumer needs it. The results are those of `vivado_synth`. The outputs follow `vivado_alt_synth`, which also runs Vivado in non-project mode, and the settings of the same names switch them on. `write_checkpoint` writes the routed checkpoint `checkpoints/post_route.dcp` (`checkpoint_route`) and the one after placement beside it. `write_netlist` writes the functional netlist `outputs/impl_funcsim.v` (`netlist`) and the constraints `outputs/impl.xdc` (`xdc_exported`). `write_timing_netlist` writes the timing netlist `outputs/impl_timesim.v` (`netlist_timing`) and its slow-corner SDF `outputs/impl_timesim.sdf` (`sdf`). `bitstream` writes the bitstream. The flow does no synthesis, so it has no `checkpoint_synth`. Vivado finds the top module of an EDIF netlist by the name of its file. The flow therefore copies the netlist to `<top>.edif` in its run directory, whatever the file was called. For that, the design needs `rtl.top`. It also needs `fpga` and a clock, as for any Vivado flow. Pin constraints are `Xdc` design sources or `xdc_files`. A netlist from another source must be flat and must carry the ranges of its buses. Use yosys's `write_edif -pvector bra` after `synth_xilinx -flatten`. The flow reads the netlist before it starts Vivado. It stops for a netlist that is not flat, and it names the modules. It cannot check the ranges. Without them, Vivado links the design with every bus reversed and gives no message.

Required settings: `fpga`
